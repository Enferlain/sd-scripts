# Review: training GIL rule, call setups, default-stream optimizer step (2026-11-27)

Scope: uncommitted diff of `library/training/trainer.py`, `library/training/preparation.py`,
`library/runstate/generation.py`, new `library/performance/precision.py`, and commit 207e264a
(`library/training/units/prepared.py`, `owner.py`, `library/optimization/construction.py`).
Context read: `library/iro/gil.py`, `library/iro/runtime/{calls,coordinator}.py`, `library/iro/devices/pytorch.py`,
`library/runstate/preparation.py`. Nothing was run. Stream ordering in `_step` was checked against the
adapter's one-stream-per-device design and found sound on the normal path (see "Checked, no defect").

## Findings

### 1. `_step` has no try/finally: a failing step leaves the adapter stream unordered after the default stream
`library/training/units/prepared.py:259-262`

```
default.wait_stream(current)
with torch.cuda.stream(default):
    prepared.optimizer.step()
current.wait_stream(default)      # skipped if step() raises
```

Defect: if `optimizer.step()` raises (bitsandbytes CUDA error, OOM allocating 8-bit state on first step,
a non-finite-guard in a repo optimizer), `current.wait_stream(default)` never runs. Kernels already queued
on the default stream (partial parameter/state updates, reads of `p.grad`) stay unordered with the adapter
stream.
Scenario: the call fails and the run unwinds, but the runtime still releases leases, frees gradients
(`zero_grad`, tensor drops) and runs held-setup undos on the adapter stream. Those free blocks that belong to
the adapter stream's allocator pool while the default stream is still reading them, so the allocator can
hand the memory to later adapter-stream work. This is the hazard the wait exists to prevent. It is
low-probability but it corrupts exactly the state a failed run's settle/undo steps and any "retry from last
published generation" path would trust.
Fix: wrap in try/finally so `current.wait_stream(default)` always runs:

```
default.wait_stream(current)
try:
    with torch.cuda.stream(default):
        prepared.optimizer.step()
finally:
    current.wait_stream(default)
```

### 2. `_step` orders only the first CUDA device's streams
`library/training/units/prepared.py:251-258`

Defect: `device` is the first CUDA parameter's device. A unit whose parameters span several CUDA devices
(participants on different devices are allowed; `participants` is a mapping) steps the other devices'
parameters on whatever stream is current for them, with no `default` switch and no waits. For those
parameters the bitsandbytes race that 207e264a fixed returns (and `with torch.cuda.stream(default)` only
selects the first device's default stream, so bnb launches for other devices run on their own device's
legacy stream with no ordering either way).
Scenario: model split over two GPUs trained by one `adamw8bit` unit: parameters on cuda:1 come out
nondeterministic, as the commit message describes for the single-device case.
Fix: group parameters by CUDA device and do the wait/step/wait per device, or refuse
(`steps_on_default_stream` unit) when a unit's parameters span more than one CUDA device.
Severity: low while runs are single-device.

### 3. Route preparation still runs after a realization failed, mutating the model in place for a doomed attempt
`library/training/preparation.py:118-130`

Defect: when `realizations.get(name)` is missing or `realization(*settings)` raises, a failure is appended
and the loop falls through to `preparation(record.binding.value)`. Route preparations "may change the object
in place" (module docstring: gradient checkpointing on, etc.), and the attempt is already going to publish
`failures`, i.e. be rejected. The `requires_grad_` rewrite earlier in `_prepare` has the same property, but
this change adds a new way to reach it and it is avoidable.
Scenario: strategy says `realize(@mixed_precision, "bf16")` (typo for `bfloat16`, `ValueError` from
`mixed_precision`), the UNet's preparation enables its gradient checkpointing and the run is refused; the
bound UNet stays mutated in the authority (a refused realization is retried by a launcher with fixed settings
against the same bound object) so the retry sees a model whose checkpointing flag and `requires_grad` were
already changed by a run that never published.
Fix: after a realization failure for this record, `continue` before calling `preparation`, and ideally build
all realizations for all records before any preparation runs.

### 4. A participant's realization is only validated when the participant has a requested route
`library/training/preparation.py:112-123` (loop is over `requested` routes)

Defect: realizations are resolved and built inside the per-route loop. A participant that declares
`realize(...)` but has no LEASE route requested (Trainer derives `routes` from lease obligations with
`view is None`) never reaches that code, so a realization installed under no name, or built with bad
settings, is accepted silently, and the declared precision never applies to anything. For a participant with
two routes the same failure is also reported twice and the setup is built twice.
Scenario: a participant is only read through a view or by a custom owner, declares mixed precision, and the
launcher forgot to install `mixed_precision`: no refusal, the run reports success.
Fix: validate and build each participant's realizations once, per participant, over all participants that
declare any (requested routes or not), and share the built setups across that participant's routes (this also
makes the `s is setup` dedup in `calls.py:85-92` meaningful across routes).

### 5. `MixedPrecision` can pick the wrong device type and silently disable itself
`library/performance/precision.py:21-23, 48-55`

Defects:
- `_device_type` looks only at `isinstance(handle, nn.Module)`. The handle is the route's callable, which
  route preparation may return as a wrapper or closure (`Realization`/`RoutePreparation` contract:
  "returns the route's callable"). Then it falls back to `torch.accelerator.current_accelerator()`, so a CPU
  participant on a machine with CUDA gets `torch.autocast("cuda")`, and an offloaded module whose first
  parameter is on CPU gets `autocast("cpu")` while its compute runs on CUDA. In both cases the call is not
  in the declared precision and nothing says so. The setup does not know the device the participant is
  bound on (the adapter's device is known to `Trainer`).
- `torch.autocast(..., dtype=bfloat16)` on hardware without bf16 support logs a UserWarning and builds a
  disabled autocast; the run then trains in fp32 while the strategy declared bfloat16. D15 treats a
  silently different precision as a departure that should be refused.
- `float16` is accepted with no loss scaler anywhere in the unit/advance path, so fp16 gradients underflow
  silently. Either refuse `float16` or provide scaling.
Fix: take the device type from the adapter (pass it into the realization call as the builder's context or
resolve it at preparation from the bound object's parameters), and raise at build time if the dtype is not
supported on that device (`torch.cuda.is_bf16_supported()`), and refuse or scale float16.

### 6. GIL refusals are not `Refused` and are applied before the cheaper refusals
`library/training/trainer.py:94-96, 107-108, 123-124`; `library/iro/gil.py:keep_off`

Defects:
- `Trainer.realize` documents "raises `Refused` with the reasons at the first step that fails", but a GIL
  failure raises `gil.GilTurnedOn` (a `RuntimeError`). A launcher catching `Refused` to report refusals
  misses it and gets a raw traceback.
- `gil.keep_off()` runs first and mutates the process: it installs `sys.modules["triton"] = None` and adds a
  `warnings` error filter on every call (the filter list grows by one entry per `realize`). If the run is
  then refused by `check_implementations` (missing implementation, mismatched evidence), the process has
  already lost Triton for good, so a corrected second attempt in the same process that selects `torch.compile`
  cannot use it, and the refusal does not say why.
- The D15 refusal text should name "the declared way to go ahead" (design line 4949); the messages here
  only say what is on.
Fix: run `check_implementations`/`cold_load` first, then `keep_off()`; convert `GilTurnedOn` into `Refused`
at the three Trainer call sites; make `keep_off` idempotent (skip the filter if already installed).

### 7. `device_settings` fact can state a setting the process is not in
`library/iro/devices/pytorch.py:59-66` read by `library/runstate/generation.py:253-257`

Defect: `deterministic=True` flips process-global state (`torch.use_deterministic_algorithms(True)`,
`cudnn.benchmark=False`, `CUBLAS_WORKSPACE_CONFIG`), but constructing a later adapter with
`deterministic=False` (the default) does not undo it and records `{"deterministic": False}`.
`ExecutableRun.execute` then reports `device_settings ... ("deterministic", False)` for a run executing
with deterministic algorithms on, and a resume "applying the settings again" cannot reproduce the original
(it gets non-deterministic if it was the first adapter, or deterministic if not).
Scenario: a CUDA adapter with `deterministic=True` and a CPU/second adapter with the default.
Fix: record what the process actually has (`torch.are_deterministic_algorithms_enabled()`), or refuse
creating adapters with different `deterministic` values in one process.

## Checked, no defect
- `_step` ordering on the normal path: `default.wait_stream(current)` covers the gradients and the clip/norm
  work queued on the adapter stream; `current.wait_stream(default)` is queued before the call's completion
  event is recorded (`PyTorchDevice` records the `Recorded` after the call returns), so later work and
  `record_stream` consumers follow it. `zero_grad(set_to_none=True)` frees grads on the adapter stream after
  that wait, matching the pool they came from; optimizer state allocated inside the `default` scope lives in
  the default stream's pool and is only used there.
- Call setups scope: `MixedPrecision` is entered around each call the lease is passed to, on the call's worker
  inside `device.context` (`calls.py:run_group`), once per (setup, handle); a loss computed outside the route
  keeps its own precision as documented.
- Realizations are installed with code evidence through `setup_evidence` and checked for one-name-one-code
  (`runstate/preparation.py:_conflicting_setups`).
