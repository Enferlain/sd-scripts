# Review of uncommitted IR changes (GIL rule, realize clause, deterministic device setting, printer fix)

Scope: git diff of library/iro/runtime/coordinator.py, text.py, words/model.py, accepted.py, devices/pytorch.py, and new library/iro/gil.py (read with library/training/trainer.py, library/runstate/generation.py, library/training/preparation.py for context). No defects found in the realize parse/print round trip itself (clause order matches between reader and writer; seed/verify agree). Findings, most serious first.

## 1. A GIL failure at Trainer.realize is a RuntimeError, not a Refused (medium)

- library/iro/gil.py:55 (`check`), :68 and :70 (`keep_off`); called from library/training/trainer.py:96, :108, :125.
- `Trainer.realize` documents "raises Refused with the reasons at the first step that fails", and every other failing step raises `Refused`. `gil.keep_off()` and `gil.check()` raise `GilTurnedOn(RuntimeError)`, which escapes unconverted.
- Scenario: a launcher catches `Refused` to report refusals. A strategy whose materializer imports a module that turns the GIL on (after the check at trainer.py:108) makes `realize()` raise a bare `GilTurnedOn` traceback. The same happens when the process starts with the GIL on and `keep_gil_off=True` (the default). The run is refused, but not through the refusal channel, and it is not reported with the other reasons.
- Fix: in `Trainer.realize`, catch `GilTurnedOn` around the three calls and `raise Refused([...])` (or make `GilTurnedOn` carry the reason in the form `Refused` takes).

## 2. keep_off() permanently poisons the process, and Trainer calls it by default (medium)

- library/iro/gil.py:75-77; library/training/trainer.py:95-96 (`keep_gil_off=True` default).
- `sys.modules["triton"] = None` is never undone and there is no inverse. The filter is also process-wide. Under pytest, the per-test `catch_warnings` restores the warning filter after the first test, while the `sys.modules` block stays. The two halves of the rule then diverge across tests.
- Scenario: any process that calls `Trainer.realize()` once (a notebook, a test session without `keep_gil_off=False`, a second run in the same process) can no longer import Triton. This includes a later run whose selection does name Triton (the "first piece that needs one" the module docstring anticipates, for example `torch.compile` GPU code generation). The failure appears as `ImportError`/"triton unavailable", far from its cause. The module is also marked unavailable if an earlier `import triton` was only attempted and failed: `name not in sys.modules` is true again after a failed import.
- Fix: have `keep_off(allowed=frozenset())` skip names the run permits. Alternatively, make it a context manager or return a token that restores `sys.modules` entries it added, and remove the filter it added. At minimum, `Trainer` should pass the run's declared permissions.

## 3. PyTorchDevice deterministic setting: global mutation, never undone, and misreported (low-medium)

- library/iro/devices/pytorch.py:59-66 and :218-237.
- `_deterministic` flips process-global state (`torch.use_deterministic_algorithms`, `cudnn.benchmark`, and the `CUBLAS_WORKSPACE_CONFIG` environment variable). The adapter that did so records `settings = {"deterministic": True}`, but any later adapter built with `deterministic=False` (the default) records `{"deterministic": False}` while the process is still deterministic.
- `ExecutableRun.execute` (library/runstate/generation.py:252-256) reports each device's `settings` as a `device_settings` fact, "which a resume applies again". A run with `Cuda(0, deterministic=True)` and `Cuda(1)` reports device 1 as non-deterministic when it ran deterministic. A later in-process run with `deterministic=False` silently stays deterministic and reports otherwise. Tests in one process leak the same way.
- The mutation also happens before `torch.device(self.kind, index)` and `torch.Stream(...)`. If either raises (bad index), the process is left deterministic with the environment variable set but no adapter exists.
- Fix: either have a `deterministic=False` adapter report the actual `torch.are_deterministic_algorithms_enabled()`, or refuse mixed settings in one process (raise if the requested value differs from the current state). Apply the setting after the device and stream are created.

## 4. Watcher/settle path (low)

- library/iro/runtime/coordinator.py:201 and :227-233.
- The GIL verdict and `watcher.cancel()` sit after the awaits in `finally` (`kernel.until`, `storage.drain`, `calls.settle_holds`). If one of those raises, the watcher keeps running until `asyncio.run` tears down, and the GIL verdict is skipped entirely, so the outcome (or the exception) says nothing about the GIL. Fix: cancel the watcher in its own `try/finally`, or evaluate the GIL verdict in a nested `finally`.
- In `checked` mode when the watcher already noted the failure, `outcome.error` is first set to `"; ".join(kernel.errors)`, which already contains the GIL message. Line 233 then prepends `self._gil` again, giving "gil...; gil...". Cosmetic: build the message once, and skip the prefix if `self._gil` already appears in `outcome.error`.
- `self._gil` is not reset at the start of `run()`; correct only because a Coordinator runs once. This is harmless today but is a latent trap.

## 5. realize settings are not verified to be literals; a malformed op crashes seed (low)

- library/iro/words/model.py:63-73; library/iro/accepted.py:238-241 (`_setting` raises `ValueError`).
- `verify_` checks only that each entry starts with a symbol. Programmatically built IR (not text, since the reader only produces literals) with a non-literal setting passes verification and then fails with a bare `ValueError` in `seed`, not a refusal. The same gap exists for `settings` on materialize, so this is consistent with existing behavior but newly extended.
- Fix: in `verify_`, require each setting to be `IntegerAttr`, `FloatAttr` or `StringAttr`, matching `_setting`.

## 6. Printer fix: unprinted unused arguments reserve "%unused" names (low)

- library/iro/text.py:1281-1283.
- Binding each unprinted unnamed entry argument as `%unused` (then `%unused_2`, ...) puts those names in `Names.taken` of the body's scope. A body-local value the reader named `%unused`, bound afterwards, is printed as `%unused_2`. Name hints are not semantic, so the IR is unchanged, but printed text no longer preserves a user-written `%unused`. The override also discards the carried-type naming that `bind` would otherwise apply (for example `%Latent`), which only matters if those names are reused for later siblings.
- Fix: do not bind at all (`names.of[argument] = ...` is only needed if the argument might be referenced, and it has no uses). Skip the loop, or bind with a name that is not a valid identifier so it cannot collide.
