# Review: models, objectives and losses (commit 207e264a, UNet working tree)

Files: library/models/denoisers/sd_unet.py, library/models/sdxl/assembly.py, library/objectives/schedules.py, library/objectives/formulations/ddpm.py, library/losses/{elementwise,reductions,weightings}.py.

Result: no high-severity defect found. Checked and found correct:

- SD 1.x config (num_heads=8, conv projections, 4 levels, depth (1,1,1,0)) builds 859.52M parameters and 686 state keys. SD 2.x config (head_dim=64, linear projections, context 1024) builds 865.91M. Both match the reference counts.
- Key names match openaimodel at the Upsample/Downsample/skip positions.
- Channel arithmetic: skip stack, output-block input widths, `level and i == num_res_blocks` upsample placement.
- Heads by count or width; GEGLU, FeedForward and Transformer2DModel projection order for both projection styles.
- Checkpointing: with it on or off, CPU float32 outputs are bit-equal and all parameter grads equal (max diff 0.0) for both the SD1-like and SD2-like tiny configs, in train mode. There is no dropout and no RNG, so nothing is missed.
- Schedules, zero-terminal SNR, noising, v target, SNR and min-SNR weighting equal today's `_deprecated/ddpm.py` and Diffusers' arithmetic.

Findings, all low severity:

## 1. GroupNorm32 never computes in float32 once the loader casts to bf16
sd_unet.py:103-109 with assembly.py:73 (default `dtype=torch.bfloat16`).
- Defect: the reference's GroupNorm32 always computes `super().forward(x.float()).type(x.dtype)`. Here the float32 branch runs only when `weight.dtype == float32`. `load_unet` casts every parameter, GroupNorm weights included, to bf16 or fp16, so with the default every resnet and output norm runs natively in low precision. The class docstring states the condition, but the module's name and the reference suggest otherwise.
- Scenario: SD 1.x/2.x (and SDXL) trained or run in pure bf16/fp16 normalise in low precision, which differs from the reference run in fp16. This is the same as today's kohya code, which is why the bit-for-bit SDXL check passes, so it is a fidelity decision rather than a regression.
- Fix: decide it explicitly. Either keep the norm parameters float32 in `load_unet` (changes the bits against today) or document that the new component deliberately follows kohya, not the reference, here.

## 2. Middle block always builds an attention, even at depth 0
sd_unet.py:292 (`attention(channels, config.middle_transformer_depth)`).
- Defect: with `middle_transformer_depth=0` the middle block still gets a `Transformer2DModel` with an empty block list but live norm, `proj_in` and `proj_out`. These layers are not identity, since `proj_out` is not zero-initialised in a loaded model. The reference's `disable_middle_transformer` removes the module altogether, which also changes the `middle_block.N` indices. `attention()` also runs `config.heads(channels)` at the middle width, so a config whose middle width does not split into heads fails even though it has no attention. Per-level depth 0 is handled correctly (`if depth`).
- Scenario: a release or variant configured without middle attention gets extra unexpected keys (missing-key loading error) or, if trained from scratch, a spurious projection.
- Fix: build the Resnet, attention, Resnet triple only when depth > 0, and otherwise a two-block layout matching the reference's key indices. Alternatively, reject depth 0 in `SDUNetConfig.__post_init__`, since only SDXL is implemented.

## 3. `y` is silently ignored when the config has no vector conditioning
sd_unet.py:326-331.
- Defect: `if self.config.adm_in_channels is not None:` guards both the use and the validation of `y`. A caller who passes SDXL-style `y` to an SD 1.x/2.x UNet gets no error.
- Scenario: a wrong conditioning wiring in a future SD 1.x/2.x strategy trains without any signal that the vector is dropped.
- Fix: `elif y is not None: raise ValueError(...)`.

## 4. Size numbers are rounded to bf16 before being embedded
assembly.py:99.
- Defect: `torch.tensor(sizes, dtype=dtype)` with bf16 (8 significant bits) cannot represent integers above 256 that are not multiples of 2, 4, 8 and so on. Original sizes such as 1365 become 1360, and 1023 becomes 1024. The embedding of the original-size and target-size conditioning is then computed from the rounded value. This is faithful to today's denoiser call and is the documented intent ("as today's denoiser call makes them"). It is still a conditioning error for non-bucket-aligned original sizes, which are common (source image sizes).
- Fix: build the values in float32, embed, then cast the embedding. This changes bits against today, so it needs a deliberate parity decision.

## 5. Loader edge cases
assembly.py:57-74.
- A `.ckpt` (pickle) SDXL checkpoint fails inside `safe_open` with a safetensors parse error, not a message naming the format. Today's loader accepts both.
- All UNet tensors are read to host memory first (`state`) and only then moved, so the peak is the full checkpoint UNet (about 5 GB fp16) plus the target copies. Moving each tensor as it is read would avoid that.
- Unexpected non-UNet prefixes are ignored by design. A Diffusers-layout or ComfyUI `unet.`-prefixed file produces the "not an SDXL UNet" error listing all 5 sampled keys as missing, which is correct but unhelpful for those cases.

## 6. Minor shape and broadcast hazards in losses and conditioning
- losses/reductions.py:31-34 `weigh`: `losses * weights` with `losses` shaped `(B,)` and `weights` shaped `(B,1)` silently broadcasts to `(B,B)`. A shape check `losses.shape == weights.shape` would catch it.
- losses/reductions.py:24-28 `per_sample_mean`: a 0-dim input falls to `mean(dim=())`, which reduces everything, and `sample_mean` then raises IndexError on `shape[0]`.
- models/sdxl/assembly.py:112-121 `conditioning`: only the pooled batch is checked against the sizes; `hidden_states1/2` batch mismatches surface as a torch error from the cat, or broadcast if one is size 1.
- objectives/schedules.py:79-88 `NoiseSchedule.on` keys copies by `torch.device` object, so `cuda` and `cuda:0` each keep a copy. This is harmless, but the `quantity` string is unvalidated (`on("betas", ...)` works).
