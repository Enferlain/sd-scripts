## Findings

### 1. test_stochastic_recomputation.py:195-243 - the failing-backward test never fails inside the recompute (weak scenario)
`FailsBackward` wraps `prediction` in `failing_objective`, so it sits after the checkpointed block in the graph. Autograd runs it first. It raises before the checkpoint's recompute has started. The docstring says "as a recompute or a kernel might", but no recompute runs.
Scenario: a runtime change makes the recompute advance the activity's state and then raise partway through. This test still passes, because the activity state equals the forward's progress.
Fix: put the failure inside the recompute. For example, make `Noisy.block` raise on its second call, or put a module before the dropout whose forward raises when `torch.is_grad_enabled()` is false or on its second call. Then assert the same state.

### 2. test_stochastic_recomputation.py:183-192 - the "negative control" tests PyTorch, not the system
It seeds the default CUDA generator with 1 and then 2 and asserts the two dropout outputs differ. That is true of any dropout and says nothing about whether test 1 (line 166) can fail.
Scenario: the runtime stops giving the window its own random state. `checkpoint(use_reentrant=False)` has `preserve_rng_state=True`, which stashes and restores RNG state in the recompute by itself. Test 1 may then still pass on `checkpointed == plain == expected`. Only the `set(device.random.states) == {OWNER}` assertion would catch the regression.
Fix: make the control an actual run. Run `through_the_trainer` with the checkpoint's RNG preservation disabled (`preserve_rng_state=False` via a flag on `Noisy`) and assert `checkpointed != expected`. Or use a model that draws from the default generator by hand. That shows the oracle can fail.
Related: line 174's "the recompute drew exactly what the forward drew" is largely guaranteed by torch's checkpoint, not by the runtime. Say so, or assert on the runtime's own states.

### 3. test_gil.py:113-132 - the periodic-watch case cannot fail if the watch is broken, and neither case proves which check fired
Parametrized `(0.5, "the periodic watch")` and `(0.0, "the check as the run settles")` both assert only `out[0] == "failed"` and the same message. `found_by` appears only as an assert message.
Verified in coordinator.py:229-233: the settle-time `gil.enabled()` check sets the identical message and `failed` status. With `wait=0.5`, `after()` finishes after the GIL is already on, and the run settles about 0.5 s later. If `_watch_gil` were deleted, the 0.5 case would still pass through the settle check. With `wait=0.0` a race between the 0.05 s watcher and the settle check decides which fires, so that case does not isolate the settle check either.
Fix: make the call block until the watcher has acted, then assert the watcher fired. For example, in `load()` turn the GIL on and then wait (up to a timeout) for `kernel.errors` to contain the message, or make the callable sleep 1 s and assert the outcome's error was noted before the callable returned. For the settle case, use `watch_gil=3600` so only the settle check can find it. Then the 0.0 case is deterministic.

### 4. test_gil.py:41-56 - the first case passes vacuously if Triton is not installed
Without Triton, `find_spec("triton")` is `None` and `import triton` raises `ImportError` even if `keep_off` did nothing. The output is `spec None unavailable state off`, and the test passes. The module docstring says "the environment provides" Triton, but nothing asserts it. Test 2 would fail with a confusing `ModuleNotFoundError`, but test 1 would not.
Fix: in the script, assert `importlib.util.find_spec("triton") is not None` before `gil.keep_off()` (or `pytest.importorskip` in the parent via `find_spec`).
Also, `fresh()` inherits `os.environ`. A parent with `PYTHON_GIL=0` or `1` changes what the subprocess sees. Clear it in `env`.

### 5. tests/unit/training_core/conftest.py:9-11 - `gil.keep_off()` at import only half works under pytest, and only some sessions get it
Three points, two of them verified:
a) Verified with a probe conftest and test in a scratch dir: the `warnings.filterwarnings("error", ...)` that `keep_off` installs is gone by test time. Pytest's collection and per-test `catch_warnings` contexts revert it. Only the `sys.modules["triton"] = None` block survives. The comment "keeps it off for every run in it" is therefore not true. A mid-session import that enables the GIL is only a warning, and nothing fails until some later `Trainer` calls `gil.keep_off()` or `gil.check()`. Each `Trainer` re-applies the filter per run, so the runs themselves are covered.
b) Verified: in `uv run pytest tests/unit` the root tests/conftest.py imports torchvision, which loads Triton, and the GIL is on before this conftest runs. `gil.enabled() is False` is false and nothing is blocked. The guard is only active in sessions that skip tests/conftest.py (`--confcutdir=tests/unit/training_core` or `tests/unit/iro`). That does not break other packages in a full `tests/unit` run. In the confcutdir sessions, it is collection order that decides: any module collected earlier that imported Triton leaves the GIL on and the guard off, silently. `KEEP_GIL_OFF` in test_units.py:96, test_realizations.py:36 and test_stochastic_recomputation.py:36 is likewise frozen at import time.
c) Cross-package effect where the guard is active: Triton stays unavailable for the whole session, from conftest import through later collection and the run. Verified in a probe that `import bitsandbytes` still works (0.50.2) but `torch.utils._triton.has_triton()` becomes False, and torch logs "triton not found". So a test in a later-collected package that depends on Triton, torch.compile's GPU path or a Triton kernel would silently take another path or fail. This is not currently triggered: the repo's torch_compile tests mock the compile step, and the bitsandbytes tests use `importorskip` and bitsandbytes imports fine.
Fix: do not mutate process-global import state in a conftest import. Use a session fixture or `pytest_configure` that is explicit about it. Better, drop the conftest side effect: tests that need the GIL rule already pass `keep_gil_off` to the `Trainer`. At minimum, correct the comment and document that it needs `--confcutdir`.

### 6. test_sdxl_step.py:313-317 - the tensor comparison does not assert the key sets are equal
`differing = [name for name, value in ours.items() if not torch.equal(value, reference[name])]` only visits our keys. The reference has 17 tensors (`context, grad_l2, grad_norm, grad_sample, grad_sum, loss, noisy_latents, output, param_l2, param_sample, param_sum, per_sample_loss, snr, squared_error, target, timesteps, vector`). Ours has 10: the 9 recorded by `seen(...)` plus `grad_norm`.
Scenario: `seen("target", ...)`, `seen("output", ...)` or the `final` loss recording is dropped or renamed (module-global `SEEN`). The test compares one fewer tensor and still passes. A renamed key not in the reference raises `KeyError` instead of a clear message. The docstring promises "the UNet's inputs and output, the target, the losses, the gradient norm and every parameter".
Fix: `assert ours.keys() == EXPECTED_NAMES` (a literal set) before the comparison. The parameter hashes already cover the gradients indirectly, since params are after the AdamW8bit step; the `grad_*` and `param_*` reference tensors are unused.
Also: the test is tied to this machine (hard-coded `/mnt/d/...` checkpoint and `index = 1 if device_count() > 1`). It skips silently elsewhere, and on a different GPU a bit-for-bit mismatch is a failure rather than a skip. State the GPU in the reference record and skip when it differs.

### 7. test_sdxl_window.py:299-304 - the comparison run is never compared to anything, and the validation values are not checked
- `coordination["losses"] == comparison["losses"][:6]` only shows the two runs agree with each other. If the new training path is wrong (for example the unit never steps, or the weights are not updated), both runs are equally wrong and the test passes. The only checks on the comparison losses are `len == STEPS` and not NaN. The recorded step-0 loss is available in `reference/finetune_step_000.safetensors` (`loss`), and `test_sdxl_step` is a stricter test of step 0. But steps 1..49 are unchecked, as is that the loss responds to the updates. For example, `losses[3:]` could equal `losses[:3]` forever (BATCHES cycles 3 recordings) and nothing would notice.
- `validations` is only checked for the step indices `0..5`. The values (`float(loss)`) are never asserted finite, or to change between steps. `validate_loss` uses the same fixed batch (`produce(0)`), so a handler reading live weights must give a different value after each step, and a handler reading stale or a copied snapshot would give a constant. The test name and docstring claim "protected reads of the UNet's live weights".
Fix: assert `comparison["losses"][0]` equals the reference `loss` bit for bit (both runs use deterministic = True; same card), assert the validation values are finite and pairwise distinct, and assert the training losses are not all equal.

### 8. test_sd_unet.py:101-103 - the checkpoint-point test accepts a missing instance
`{type(m).__name__ for m in unet.checkpoint_points()} == {...}` is a set of names. If a block type loses some of its instances from `checkpoint_points()` (for example only the first `ResnetBlock2D`), the test still passes.
Fix: compare counts per type with `sum(isinstance(m, T) for m in unet.modules())` for the four types.
Also (low): test_sd_unet.py:117-121, `test_a_vector_of_another_dtype_or_batch_is_refused`, only exercises the dtype half. A batch-size mismatch is never tried, though the name claims both. Add `y[:1]`.
Also (low): `small()` calls the global `torch.manual_seed(0)` (and `Noisy`'s `model()` in the stochastic test, plus `torch.cuda.manual_seed(1/2)` at test_stochastic_recomputation.py:188-190, and test_units.py:77) and so resets the process-global RNG for whatever test runs next. Nothing found depends on unseeded randomness today. Use a local `torch.Generator` or save and restore the state in a fixture.

## Not findings (checked)
- test_realizations.py: oracle is the autocast state seen inside each call (`SEEN`), cleared per test; the "outside the route" case does check `False` for the objective. `SEEN` and `BATCH`-style module state is reset by every test that reads it.
- test_device_settings.py: all three cases run in fresh processes, so the process-global `torch.use_deterministic_algorithms(True)` and `os.environ` writes do not leak. In-process `Cuda(...)` elsewhere never sets `deterministic=True`.
- test_sdxl_step.py / test_sdxl_window.py run in fresh processes; their module globals (`SEEN`, `BATCH`, `LOSSES`, `VALIDATIONS`, `MODE`) cannot leak between test runs. `test_sdxl_window` imports `test_sdxl_step` as a module, which is harmless.
