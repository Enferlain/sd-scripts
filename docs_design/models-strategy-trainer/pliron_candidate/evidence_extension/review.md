# Review: Pliron 0.20.0 independent pair/frozen-resource extension + resource-aware legality analysis

## Summary

I read the new/changed files directly (contract.rs, pair_extension.rs, dialect.rs, prepare.rs, lib.rs, main.rs, bridge.py, pair_extension.py, __main__.py, test_extension.py, test_b.py, README, evidence files, .gitignore, requirements.txt, CHANGELOG, ROADMAP), the two provided extension artifacts, and the reused xDSL target modules needed to validate the integration claims. The implementation matches the stated intent, and the important negative controls hold up under scrutiny. I found no correctness or authorization bug in the exercised paths; the findings below are low-severity robustness/reporting/documentation issues.

## Verified claims

- **No extension-name dispatch in core.** A grep for `pair`/`pairing` across `native/src` hits only `pair_extension.rs` and the module declaration in `lib.rs:3` (the `pairs()` helper in prepare.rs is unrelated). Core (`contract.rs`, `dialect.rs`, `prepare.rs`, `main.rs`) works purely through `LocalStageInterface` / `PayloadTypeInterface`; the generic SSA chain check in `prepare.rs:232-326` threads nested input/output types correctly.
- **Factory ordering.** Lowering happens only inside `_materialize` (bridge.py:138-159), which runs after the native request in `prepare` (bridge.py:69-71) and after *both* the native request and the saved-manifest comparison in `load` (bridge.py:73-93). Snapshots are built per-call from declared `call["resources"]` only, wrapped in `MappingProxyType`; the interruption test additionally asserts identity (`snapshot is extension.COEFFICIENTS`).
- **Forged cross-barrier group.** `load` computes `ResourceReport` from the verified semantic snapshot (prepare.rs:1028-1034), not from the chain, then rejects any fused member without `permits()` (prepare.rs:1077-1083). I traced the forged test: it rewrites the *unfused* opaque artifact (so braces stay balanced) with all four attrs still valid, and rejection comes from the analysis, not a parse error. Sequential indexing (prepare.rs:1045-1094) also prevents reordering/skipping, and consumer-chain fusion/single-stage groups are rejected (prepare.rs:1050-1057).
- **Analysis cache/preservation.** `FusionPass` preserves `SourceAnalysis` + `ResourceAnalysis` (prepare.rs:913-914), the trailing `Observe` asserts cached == freshly recomputed report (prepare.rs:871-875), and `computations == 1` is consistent with the pipeline in both fused and unfused runs. Dispatch tuples `(4,1,1)→(1,2,1)/(3,2,1)` match the checked-in artifacts and `analysis_evidence`.
- **Schema 2 / EOF / packaging fixes preserved.** `parse` composes `spaces().skip(eof())` (prepare.rs:104-115), schema 2 is enforced at every manifest boundary (prepare.rs:479-482; bridge.py:130), B artifacts were regenerated, and `!requirements.txt` (line 4) correctly re-includes against the root `*.txt` rule (same mechanism as the xDSL sibling, which carries an explanatory comment this one lacks). 12 rejection + 3 whitespace new cases match the 15-case claim; 103+15=118 and 118+72=190, 190+261=451 all check out. I counted the `test_extension.py` parametrizations: exactly 72.
- **No runtime/owner/backend drift.** `list_changed_files` shows no `xdsl_candidate` modifications; the reused `runtime.py`/`local_runtime.py`/`payloads.py` are untouched.

## Findings

1. **`installed()` silently discards codecs (and dialects) of legacy xDSL registries — bridge.py:45-48.** When a `preparation.Registry` is adapted, only `name/bindings/resources` are carried; codecs fall back to `{"record": INTEGER}` and signatures to `("record","record")`. This is currently benign (`fixture.registry()` uses defaults, and `test_b.py:52` exercises this path), but for a registry that installed non-default codecs the manifest would misdescribe the installation and fail at the native boundary with a codec-mismatch attribution instead of pointing at the adapter. Since legacy codecs are keyed by `FlowType` they can't be passed through as-is; an explicit guard ("legacy registry installs non-default codecs") would fail with a clearer message.

2. **`unknown_sources` under-reports a `may_effect` stage that declares frozen reads — prepare.rs:697-704.** `unknown_sources` only collects calls with `resources == None`. A hypothetical extension describing `resources: Some(...)` with `effect: "may_effect"` (permitted by the public interface; the Python manifest builder supports it at bridge.py:111-115) would be correctly declined for grouping and listed in `reads`, but omitted from `unknown_sources` even though its effect footprint is still unknown. The shipped ops can't produce this combination, so this is a reporting-semantics note for the generic interface, not a live bug.

3. **Duplicated reserved-outcome vocabulary — prepare.rs:288-295 vs `xdsl_candidate/payloads.py` `RESERVED_OUTCOMES`.** The reserved names are hand-copied (the base outcomes were properly shared via `BASE_OUTCOMES`). If one list changes, accept-time and runtime-reserved sets can diverge silently. Same class of issue as the pre-existing literal `"0.20.0"` strings in prepare.rs/main.rs that must track the `=0.20.0` Cargo pin.

4. **README reproduce section omits the opaque cold-load invocation.** The three new commands dump `/tmp/pliron-pair` and `/tmp/pliron-opaque`, and the shown `--extension --load /tmp/pliron-pair/artifact.json` pattern will not work for the opaque artifact without also passing `--opaque` (registry mismatch → rejected, with a clear but non-obvious error). One extra line (`--extension --opaque --load /tmp/pliron-opaque/artifact.json`) would close the trap.

5. **Minor diagnostics/robustness nits (no action required).**
   - `describe()` emits `"codec": ""` when a binding's output schema has no installed codec (bridge.py:110-121); rejection happens natively with attribution, but rejecting in `describe` would localize the error.
   - `ResourceReport::from_plan` and the load-side analysis use `expect(...)` panics (prepare.rs:689-693, 1030-1031) rather than the `Checked` channel; unreachable after prior verification and consistent with existing style, but a panic crosses the subprocess boundary without a message.
   - `pair_extension.py::build()` performs ordered-substring surgery on printed IR (`text.replace(...)`); it's pinned by tests, just fragile if attribute printing order ever changes.

## Notes on things that looked suspicious but check out

- The fused-opaque artifact's producer chain contains a pre-existing `exec.fused` wrapper, which is why the forged test deliberately uses the unfused artifact — the reconstructed document stays brace-balanced and the rejection is genuinely from resource analysis.
- Cold `load` accepts any in-order grouping of individually-permitted stages (not only the matcher's run-splitting); this was an accepted review position from the previous milestone and remains documented behavior.
- `plan_attrs` recomputes `accepted_hash` from the freshly parsed accepted text (prepare.rs:1008-1011), so the plan is bound to the supplied document independently of the structural-equivalence check.
- Evidence internal consistency: identical report hashes for `unfused`/`opaque_unfused` are expected (opaque offset is numerically equivalent); `review.status: "pending"` correctly reflects that this review is the qualification's pending review.
