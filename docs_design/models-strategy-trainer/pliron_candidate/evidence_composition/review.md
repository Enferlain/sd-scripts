## Intent match — verified core mechanics

I traced the full mechanism rather than trusting the docs; the implementation does what the case document claims:

1. **Native semantic verification and target limits** (`composition/mod.rs`): `collect()` checks attributes against `CompositionContract` descriptions (exact key set), operand/result types, region count/kind/arity, and resolves operands through region-argument aliases with a cycle guard. `verify()` enforces: producer stop operand is a sibling group enclosing every stream consumer; settle/finish include **all and only** direct-child obligations (BTreeSet comparison); request eligibility (`after_window ≤ max_windows`), once-only multiplicity, exactly one recipient; evaluator stream/model association with the repeat source; complete ordered take/contribute pairs with gradient chaining, `normalization == window cardinality`, and advance consuming the final gradient. `profile()` then narrows to the bounded target (one of each scope, 2×2 windows, after_window 2, horizon 3 / ready 2 / workers 1, frozen encoder, exactly 2 models, scalar `weight`, homogeneous objective bindings) — correctly separated from semantic acceptance, which the `windows:3`/`horizon:4` tests confirm ("semantically valid but unsupported").
2. **Admission precedes claims**: `choose()` commits the whole `Sequence` Choice before any Join/claim work; `stop_before`/`stop_after` tests exercise both sides of the boundary, and partial-window cancellation retains `acquired={0:[0,1],1:[2]}`, pending work, `steps=1`, weight 0.77 — exactly as documented.
3. **Bounds**: aggregate outstanding ≤ 3 via `BoundedSemaphore(3)` released only on `consumed`; a *separate* cross-port ready budget of 2 independent of per-channel capacity 2; `Workers(1)`. The conformance oracle independently re-derives outstanding/ready sets from the journal event stream and asserts the invariants, and the live witness pins the exact `{4: claimed, 5: ready, 6: physical}` shape. The doc's "port capacity alone does not establish the aggregate bound" is genuinely implemented.
4. **Grouping/request/failure relationships**: pending request keeps the group alive with no learner mode/access acquired (late witness asserts `receipt is None`, group unsettled, training clock < witness < evaluation clock); D completion requests P stop while root completion waits both (clock ordering asserted; shutdown witness shows physical work 6 still live and readers present); either child failure shuts the producer down via enclosing-cancellation with `cleanup` awaiting the *actual* group activity exit (including failure) — no cycle, since D never awaits P.
5. **Physical protection**: encoder reads span worker execution with provenance stamped pre-physical and re-checked at admission (`product.provenance == (projection.stamps[encoder],)`); scalar output validated after physical return; evaluation holds learner reads through physical return (`readers` non-empty asserted at the witness; `gradients=False`/eval-mode observed *inside* the worker).
6. **Before-entry cancellation**: both `production_body` and `measurement` re-raise `NotEntered.cause` (not the wrapper), preserving CancelledError classification; the deterministic monkeypatched regression proves `entered=False, physical_done=True, terminal[6]=="discarded"`, and the unentered-evaluation test proves the input is reported `closed_unconsumed`, not fabricated as consumed.
7. **Truthful outcomes**: `notify()` is a strict state machine (selected→ready→claimed→consumed, `OutOfBounds` otherwise); cleanup raises if a *normal* group completion left an unsettled claim; failed physical keys become `"failed"` while completed evaluation/updates survive (late_failure and cancel_failure reports + replay assertions). This matches "truthful consumed/failed outcomes".
8. **Oracle/archive independence**: conformance is stdlib-only with independent rational arithmetic (I verified by hand: gradients 3 and 13.5, weights 0.77/0.635, prediction 6.35, loss 0.91125); replay blocks torch/xdsl/execution_candidate/composition_runtime/author imports and asserts absence from `sys.modules`; the doubled-objective test proves a wrong-but-plausible shared implementation is caught numerically; the erased run still passes all structural/liveness checks with `histories=False` while clocks/terminal/high-water survive as owner facts.
9. **Cold verification before factories**: native `load` rebuilds the expected plan fresh (manifest embedded in plan attributes) and requires structural equivalence of the saved plan; Python then requires exact saved-manifest equality; saved `profile`/`nodes` are provably ignored (garbage-substitution test runs correctly); all three rejection boundaries assert zero factory invocations; fresh-process tests (normal and `-O`) forbid authoring and xDSL parse/create/prepare while the normal parent runs the oracle. Verified projection is deeply snapshotted (`MappingProxyType`) with mutation tests.
10. **Torch-free path**: `composition.py`/`composition_author.py`/`composition_conformance.py` never import torch at module level; `composition_runtime` is imported lazily only in `materialize`/`pressure`, and `importorskip("torch")` precedes the runtime import in the owner test module — consistent with 47 document tests passing in the Torch-free env.

## Findings

1. **Low — Python 3.14-only syntax** (`composition_demo.py`, `pressure`): `except asyncio.CancelledError, BaseExceptionGroup:` uses PEP 758 paren-less multi-except. It's a `SyntaxError` on ≤3.13. The pinned env is 3.14.5 free-threaded, so this is fine there, but the rest of the code is 3.10+-compatible; parenthesizing costs nothing and avoids a surprise if the experiment is ever rerun on an older interpreter.
2. **Low — error typing on malformed artifacts** (`composition.py`, `verify_saved`): a saved artifact missing `accepted`/`prepared`/`manifest` raises `KeyError` rather than `Rejected`. There is no bypass (materialization still aborts before factories), but the diagnostic-quality asymmetry with the deliberate schema/target checks is a small wart.
3. **Low — manifest equality stricter than native check** (`verify_saved`): `artifact["manifest"] != installed` rejects a saved artifact when the installed registry gains even an *unused* binding, whereas native `check_manifest` only validates bindings referenced by nodes. This matches the documented "exact agreement" policy and is fail-closed, but it means previously saved artifacts are invalidated by additive registry growth — a compatibility consequence worth stating explicitly in the case doc (currently only "installed/saved binding agreement" is claimed).
4. **Info — erasure-point accounting vs doc**: `composition_case.md` says histories are erased "during a partial window, a pending request, physical use **and final handoff**", but `archive_erasure_points` records three; the fourth erase happens inside `CompositionRun.run()` (before `report()`) and isn't appended. Implementation and test agree on three; the doc slightly overstates the recorded points. (The `run_settled` mark is also erased before reporting — consistent with `report["events"] == []`.)
5. **Info — test-gate timeouts**: blocking gates use fixed 30s waits and witnesses 10s `wait_for`s. A regression that never releases a gate costs up to 30s per test rather than failing fast. Acceptable for research tests.
6. **Info — shutdown accounting relies on ordering**: `cleanup` disposes ready tickets without releasing the ready/capacity semaphores. This is safe only because cleanup runs after the production loop has fully exited (verified through `prepare.producer`'s task lifecycle: implementation joined/cancelled before `phase="cleanup"`). The invariant is real but implicit; a one-line comment in `cleanup` would protect future edits.

No logic errors, security risks, or authority bypasses found: every rejection boundary (accept/prepare/load/manifest) precedes model factories; the notification adapter only *observes* existing `progress.activity` exits and cannot decide completion; name-prefix tests demonstrate identity names are data, not dispatch.

## Framework contribution vs. reused owner mechanics

The split claimed in `composition_case.md` is accurate and, importantly, not overstated:

- **Genuinely new (framework contribution)**: the `lc` dialect with typed ops/regions/interfaces, whole-document interface-driven verification, the `lc_exec` plan construction with fresh-context structural-equivalence round-trips, and the cold-correspondence protocol (fresh expected plan + embedded manifest) before any Python factories.
- **Reused, not new**: all execution ownership — `Engine`, `Together`/TaskGroup lifetimes, `Repeat`/`Requested`/`Sequence`, `Feed` handoffs, leases/protection, `Workers` physical draining — is the existing `execution_candidate` machinery. The new Python runtime (`composition_runtime.py`) is binding installation, ticket/budget bookkeeping, routing, notifications, and test gates on top of it. The document says exactly this ("this is not an independent Rust ownership implementation") and keeps xDSL as the baseline with no production selection.

**Verdict**: The implementation matches the stated intent, the bounded claims are supported by the code and tests, and the evidence is internally consistent. Only minor polish items (findings 1–4) remain; none block the stated experimental purpose.
