I think Q4 is on the right semantic center, and the repo pressure test strengthens it. I’d make a few refinements before calling it settled, mostly around **what “artifact view” means, consistency, and bundle/completeness semantics**.

The current code very clearly supports your split. Accelerator resume state is its own flow, and the adapter code explicitly documents export persistence as separate from `accelerator.save_state()`.   Meanwhile SDXL manually unwraps its denoiser/text encoders and hands those family-specific objects to conversion code, exactly the kind of extraction/serialization coupling your proposal would separate.

## 1. I would make the core answer even less object-oriented

This line is excellent:

> Persistence should not “save an object.”

I’d go one step further:

> **Artifact persistence operates on semantic state ownership, not component objects or execution bindings.**

That matters especially after Q3.

Consider LoRA:

```text
logical participant:
    adapter.style

runtime representation:
    injected modules distributed through denoiser submodules

execution route:
    denoiser.training

artifact:
    adapter.style delta
```

There may be no single Python object whose `state_dict()` naturally equals the semantic artifact.

Current code happens to have an adapter runtime and calls `save_weights()` on it, but even the repo calls this an adapter-specific export contract, not universal persistence.

So the abstraction shouldn't ultimately be:

```text
component
    → artifact module
    → state_dict
```

but something closer semantically to:

```text
artifact product requests state owned by:
    adapter.style

runtime extraction knows:
    where that state currently physically resides

serializer knows:
    how adapter.style state is represented externally
```

That survives injected adapters, shared containers, sharding, FSDP, side networks, merged states, etc.

## 2. “Logical artifact view” needs one qualification

I like the term, but I would define it explicitly as a **semantic projection**, not necessarily a view of the logical/original binding.

Otherwise someone will eventually read:

```text
logical artifact view
```

as:

```python
loaded_component.original_module.state_dict()
```

which is precisely what we don't want.

Under DeepSpeed/FSDP, the *current authoritative weights* may only be correctly obtainable through infrastructure-aware consolidation of prepared state.

So I'd say:

> A logical artifact view is a purpose-specific projection of authoritative current state, indexed by logical component identity and relationships. Its physical extraction may require prepared execution state, distributed infrastructure, or capability-owned runtime state.

Thus:

```text
logical identity
    tells us WHAT state belongs in the product

runtime/infrastructure
    tells us HOW to obtain coherent current state

serializer
    tells us HOW that state appears externally
```

That separation is probably the most important thing Q4 can establish.

---

## 3. Consistency should be a first-class semantic requirement

Your:

```text
consistent state point
  selected arrangement/state revision
```

is right, but this is worth making an invariant rather than merely a pipeline stage.

For example, this must be forbidden:

```text
denoiser       from step 501
adapter        from step 500
EMA            from step 498
metadata       says step 501
```

even if each individual extraction succeeds.

Likewise with an SD3 bundle:

```text
mmdit  → state at T
vae    → state at T
clip_l → state at T
clip_g → state at T
t5     → state at T
```

where "T" means one coherent persistence boundary, not necessarily a literal shared version counter.

The Trainer/execution mechanism should own establishing that boundary because it knows:

* whether an optimizer step is in progress;
* whether gradients are synchronized;
* whether all ranks must participate;
* whether state consolidation is required;
* whether asynchronous update machinery exists;
* what global step/epoch the artifact represents.

So I’d strengthen your responsibility table:

```text
Trainer
  artifact timing
  coherent persistence boundary
  execution quiescence/synchronization
  destination/retention/publishing coordination
```

The persistence capability should not independently decide when it is safe to snapshot.

This nicely parallels the architecture we've been building: **strategy says what; Trainer guarantees execution mechanics.**

## 4. Artifact completeness is absolutely the next hard problem

I agree with your four categories, but I think there are actually **two axes** hiding inside “completeness”:

```text
semantic coverage
    what logical state does this artifact claim to represent?

physical closure
    does the artifact physically contain everything required to use it?
```

For example:

### Full self-contained model

```text
semantic coverage:
    denoiser
    VAE
    text encoders

physical closure:
    all included
```

### Adapter delta

```text
semantic coverage:
    adapter.style

physical closure:
    intentionally incomplete as a runnable model

dependency:
    base realization X
```

### Referential model artifact

Could semantically represent a complete pipeline while physically referring to external pieces:

```text
semantic coverage:
    denoiser
    autoencoder
    conditioning

physical members:
    denoiser weights
    autoencoder reference
    text-encoder references
```

That's slightly different from a delta. Nothing necessarily means "apply these changes to base weights"; it simply isn't physically closed.

So I might phrase the dimensions as:

```text
artifact coverage
  selected participant/state closure

dependency semantics
  standalone
  delta-over-base
  external-reference

physical packaging
  single file
  directory
  shard set
  multi-file bundle
```

That avoids making `bundle` another kind of completeness. A bundle is really **packaging/cardinality**, orthogonal to whether it's self-contained or referential.

An SD3 bundle can be self-contained.

An adapter bundle can still be delta-based.

A directory can be referential.

That decomposition feels cleaner.

## 5. The SD3 case strongly argues for product vs members

The branch currently does exactly what you described: `save_models()` writes the MMDiT+VAE main safetensors file and then optional CLIP-L, CLIP-G, and T5 sidecars, returning all their paths.

Then `Sd3CheckpointingStrategy.save_model_checkpoint()` iterates those paths for upload but itself returns `None`.

That suggests we need a distinction like:

```text
artifact product
    one semantic requested result

artifact members
    one or more physical outputs realizing it
```

For SD3:

```text
ArtifactProduct: trained SD3 model

members:
  main.safetensors
    covers MMDiT + VAE

  main_clip_l.safetensors
    covers CLIP-L

  main_clip_g.safetensors
    covers CLIP-G

  main_t5xxl.safetensors
    covers T5
```

This is better than saying merely:

```text
saved_paths: list[str]
```

because each member has semantic meaning.

And this exposes an actual current weakness: metadata is only passed to the main SD3 `save_file`; `_save_sidecar()` writes sidecars without it.  Whether that's desirable for the final format is a separate question, but the current persistence surface doesn't give us a rich enough product model to even describe the difference cleanly.

## 6. I strongly agree that pre-save declaration and post-save fact are different

Current Trainer does:

```text
mode says artifact role
mode resolves format
strategy resolves artifact facts
metadata gets built
then serializer runs
```

and `save_checkpoint()` gets no concrete product result back.

That's mixing **intent** and **observation**.

I'd explicitly distinguish:

```text
artifact declaration / request
    what should be produced

artifact plan / resolved product
    participants
    dependencies
    format
    expected members/structure
    serialization constraints

artifact result
    what was actually produced
```

The result can then contain facts such as:

```text
product identity
member paths
member roles
participant coverage
actual serialization format
sizes
checksums
dependency references
possibly emitted artifact/model realization identity
```

I wouldn't require every one of those fields yet. The semantic point is:

> Post-write facts must come from the completed persistence operation, rather than being inferred exclusively from the pre-write request.

That's especially useful for publishing/observation. Trainer currently fires `EVENT_CHECKPOINT_SAVED` immediately after a mode method returns, without any typed description of what it saved.

## 7. I'd slightly alter the responsibility split

Your split is almost exactly what I'd use, with one change:

```text
Strategy-selected persistence capability
  artifact role
  included logical participants
  completeness and dependency semantics
  required conversions
```

I would move **required conversions** downward.

Something like:

```text
Persistence capability / strategy
  product semantics
  participant selection
  dependencies
  completeness requirements
  supported external representation(s)

Runtime/distributed extraction
  obtain coherent authoritative state
  gather/consolidate as required

Domain serializer
  key conversion
  tensor layout
  dtype conversion where representation requires it
  sharding/file organization
  format-specific metadata embedding
```

Why? Because:

```text
SDXL full model should be safetensors
```

is product selection.

But:

```text
UNet key foo.bar must become model.diffusion_model.foo.bar
```

belongs to the SDXL serializer/conversion layer.

Likewise `save_dtype` feels like an artifact serialization policy resolved from user configuration + product constraints, not strategy behavior per se.

The current SDXL code demonstrates this nicely: strategy checkpointing currently does both participant selection/unwrapping and invokes family conversion routines.  Q4 gives us the chance to separate those.

## 8. Resume checkpoints should probably stay even more separate than “another persistence capability”

I would preserve your umbrella conceptually:

```text
persistence
  ├── runtime resume
  └── trained artifacts
```

but **not** try to force both through the same request/result contract.

They have fundamentally different identity and completeness semantics.

A runtime checkpoint asks:

```text
Can this execution resume coherently?
```

It cares about:

```text
model execution state
optimizer
scheduler
scaler
RNG
loop position
backend state
feature-owned resume state
```

An artifact asks:

```text
What trained thing did this run produce?
```

It cares about:

```text
logical participants
artifact role
dependencies
external format
provenance
model realization
```

The repo already has this distinction explicitly in adapter state I/O: accelerator checkpoint-resume is separate from export-style adapter load/save.

So I would record that as a stronger invariant:

> Runtime resume snapshots and trained artifact products share Trainer-controlled timing/consistency infrastructure, but they are separate persistence contracts and must not be unified merely because both write files.

That will prevent us from inventing one horrible `PersistenceRequest(kind=...)` abstraction later.

## EDM2 also validates the model

The current fine-tune mode special-cases EDM2 by detecting `"_edm2_loss_weights"` in the filename and then interpreting `target_model` as an object with `save_weights()`. Otherwise the exact same method routes to full-model checkpointing.

That's basically the anti-model for the future API:

```text
filename pattern
    → infer artifact meaning

target_model
    → meaning depends on artifact type
```

Under the Q4 model it becomes straightforward:

```text
ArtifactRequest
  product: edm2_loss_weights
  participant: objective.edm2_weights   # exact identity/name TBD
```

and the owning capability provides the state extraction/serializer behavior.

No mode branching. No overloaded module argument. No magic filename.

# So my Q4 resolution would be slightly stronger than yours

I'd write:

> **Persistence produces a declared artifact product from a coherent semantic projection of authoritative current state. The product identifies which logical participants and relationships it represents, its dependency/completeness semantics, and its external representation requirements. Runtime and distributed infrastructure establish a consistent persistence boundary and extract the current state required by that product; domain serializers transform that extracted state into one or more physical artifact members. Persistence never selects state by incidental Python object identity or by whichever wrapped/unwrapped object is easiest to reach.**
>
> **Runtime resume snapshots are a separate persistence contract: they capture execution state required to resume the run rather than a strategy-selected trained artifact. They may share Trainer-controlled timing and infrastructure but not artifact semantics.**
>
> **One artifact product may consist of multiple physical members, and successful persistence returns post-write facts describing the concrete product that was emitted.**

Then I'd carry these orthogonal properties forward:

```text
semantic coverage
    which participants/state the product represents

dependency semantics
    standalone
    delta-over-base
    external-reference

physical packaging
    file
    directory
    shards
    bundle

consistency
    all represented state corresponds to one valid persistence boundary
```

And one more Q3→Q4 invariant:

```text
logical component identity
    selects semantic state ownership

execution binding
    may be involved in obtaining current state

artifact extraction view
    is purpose-specific and may be derived

serializer
    never decides component identity
```

With those refinements, I’d say **Q4 is very close to settled**.

The most useful final pressure test before locking it is exactly the four cases you named, but I don't think we need to rediscover the architecture from them. We should just verify that each maps cleanly onto the model:

```text
SDXL full model
SD3 multi-member full model
adapter delta
EDM2 capability artifact
```

If none requires breaking these invariants, Q4 is done.
