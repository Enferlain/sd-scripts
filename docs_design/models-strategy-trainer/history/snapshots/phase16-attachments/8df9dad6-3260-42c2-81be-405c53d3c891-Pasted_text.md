Yeah. Given how big this has become, I’d audit it more like a **small language/runtime spec** than a normal feature proposal.

I would *not* ask one Work session to “review the whole OpenSpec and find problems.” That tends to produce a giant mixed bag where wording nits, actual contradictions, missing semantics, and speculative redesign all get blended together.

The better approach is:

```text
Pass 0   reconstruct what the spec says
   ↓
Pass 1–6 audit it from different semantic angles
   ↓
cross-pass synthesis
   ↓
fresh independent adversarial review
   ↓
only then decide whether G5 is unblocked
```

And I’d have the first Work session inspect the **actual repo**, not copies pasted into chat. The scope should include the whole `rework-model-strategy-trainer` change, the overlapping `expand-model-metadata-identity-and-structure` change, the research/design material those changes explicitly rely on, and current code only where a spec makes a claim about the existing implementation.

## The audit I’d run

### Pass 0 — Build the map before judging anything

This is important because the spec is now big enough that a reviewer can manufacture contradictions simply by misunderstanding what document owns what.

Have Work first identify:

- governing design decisions;
- normative delta specs;
- exploratory/research material;
- migration/current-code evidence;
- task completion claims;
- duplicated/shared requirements between the two OpenSpec changes;
- intentionally deferred G5 questions.

It should then create a **concept map**, not merely summarize files:

```text
authority
 ├─ participant identity
 ├─ relationship identity
 ├─ bindings
 └─ accepted transitions

preparation
 ├─ projections
 ├─ readiness evidence
 └─ executable generation

execution
 ├─ activities
 ├─ attempts
 ├─ protected uses
 ├─ outcomes
 └─ effects

optimization
 ├─ unit identity
 ├─ contribution windows
 └─ advancement

persistence
 ├─ product capture
 ├─ runtime snapshot
 └─ publication

observation
 ├─ metadata
 └─ telemetry
```

The purpose is to establish the model the rest of the audit is testing.

### Pass 1 — Authority, identity and ownership

This should be extremely mechanical.

For every major semantic thing, ask:

```text
Who establishes it?
Who owns its current truth?
Who may change it?
Who may merely observe it?
What gives it identity?
What explicitly does NOT give it identity?
What survives restoration?
What creates a new incarnation?
```

I’d make Work cover at least:

- logical run;
- participant;
- relationship;
- binding;
- route/view;
- activity;
- request/input/attempt;
- optimization unit;
- execution session;
- accepted behavior/state owner;
- realization/composition;
- catalog/source identity;
- product/member/resource;
- runtime snapshot;
- metadata observation.

This pass should hunt specifically for remnants of:

```text
Trainer = authority
strategy object = runtime authority
mode = identity
Python object = identity
path/name/role = identity
metadata = binding authority
loader success = current state
```

The G4.6 work already found several of these, so there is a decent chance there are smaller leftovers elsewhere.

### Pass 2 — Revision, version, freshness and lifecycle

I think this is probably the **highest-value audit pass** now.

Have it enumerate every distinct thing the design calls something like:

- revision
- generation
- version
- incarnation
- session
- attempt
- current
- accepted
- published
- prepared
- final
- stale

Then make an explicit matrix showing which ones can and cannot substitute for each other.

For example:

```text
participant incarnation
    ≠ binding revision
    ≠ participant numerical state
    ≠ prepared executable generation
    ≠ optimization-unit definition revision
    ≠ model realization composition revision
    ≠ catalog model revision
    ≠ execution session
```

Then search every spec for accidental substitutions.

The 4.6 correction around checkpoint-scoped `final` composition is exactly the kind of bug this pass should find. changes(8)

### Pass 3 — Execution, effects and failure semantics

Rather than reading requirements independently, trace several complete actions.

For each one:

```text
accepted meaning
→ readiness
→ admission
→ protected access
→ execution
→ backend completion
→ derivative/contribution
→ advancement/effect
→ outcome
→ cleanup/handback
→ observation
```

Then inject failure at every boundary.

I’d explicitly tell it to hunt for assumptions such as:

- Python return means physical completion;
- thrown exception means no effect occurred;
- one action has one success bit;
- gradient availability means update eligibility;
- retries are safe;
- cleanup failure erases an already-known result;
- one unit failing rolls back another;
- publication success means observation succeeded;
- absence of telemetry means work never happened.

This is where the SAM/two-pass case, partial optimizer-unit outcomes, async publication and uncertain backend effects should all collide.

### Pass 4 — Independent progress and cross-owner coordination

This deserves its own pass because it is very easy for an otherwise correct design to accidentally reintroduce a global training clock.

Treat these as independent activities:

```text
input production
cache production
training
optimization units
validation
sampling
artifact serialization/upload
metadata delivery
snapshot capture/publication
```

For each pair that can overlap, ask:

- what actually orders them?
- which shared state requires protection?
- what completion fact releases that protection?
- can one wait without head-of-line blocking unrelated work?
- does one progress coordinate get improperly used as another's state?
- is queue/arrival order accidentally becoming semantic order?

Then verify there is **no implicit global step/end-of-step/global pause** where the design claims independence.

### Pass 5 — Persistence, continuation and observation

This should deliberately compare concepts that look similar but are not.

Have Work build a matrix for:

```text
cached value
trained product
runtime snapshot
metadata snapshot
metadata history fact
telemetry observation
```

against:

```text
identity
coverage
freshness
publication
durability
admission
restoration
lineage
partial failure
external dependencies
```

The audit should prove things such as:

```text
stored ≠ published
published ≠ admissible
captured ≠ current
artifact-complete ≠ runtime-restorable
metadata-saved ≠ run-snapshot-complete
observed ≠ happened exactly once
```

The current design deliberately separates those, so this pass mainly looks for specifications that quietly collapse them again.

### Pass 6 — Pressure cases and G5 readiness

Finally, stop auditing vocabulary and try to break the entire thing.

Use a fixed set of ugly cases and trace each through **all relevant specs**, not merely the section that talks about it. I’d use:

- ordinary SDXL-style training;
- two independently due optimization units;
- routed losses with a frozen differentiable conduit;
- two-pass/SAM temporary mutation;
- independent producer using lagged model/policy state;
- cache with variant/provenance/freshness differences;
- validation feeding adaptive training state;
- staged topology replacement;
- adapter + updated base artifact;
- partially successful multi-resource publication;
- process loss with unfinished producer and optimization work;
- same-run restoration into a new execution session;
- late result from the old session;
- missing metadata/telemetry after a known runtime effect.

For each case Work should answer:

```text
What identities exist?
Who owns each state?
Which revisions matter?
What can progress independently?
What access must remain protected?
What are all possible partial/uncertain outcomes?
What can be retried?
What survives restoration?
What metadata may assert?
Which concrete G5 representation decisions remain?
```

If a case needs some semantic fact that the OpenSpec cannot currently express, **that is a real blocker**.

If it merely doesn't specify whether the implementation is Python/native/direct/generated/etc., that is *not* a blocker; that's G5 doing its job.

---

## I’d use two Work sessions, not one

The first one should do the comprehensive audit above and produce a structured report.

Then start a **fresh Work session** whose job is to attack that report and the OpenSpec independently. Don't tell it to continue the first one's reasoning. Give it the first report as evidence but tell it:

> assume the first audit may have misunderstood the architecture, missed contradictions, or incorrectly classified unresolved semantics as implementation details.

That fresh context matters. Otherwise the model will tend to defend its own reconstructed architecture.

A third short session can then reconcile genuine findings.

## Prompt I would give the primary Work session

You can pretty much paste this:

> Perform a comprehensive pre-G5 semantic audit of the current `rework-model-strategy-trainer` OpenSpec.
>
> This is not another architecture survey and not an invitation to redesign the system. G1–G4 have accumulated a large set of accepted semantic decisions. The goal is to determine whether those decisions now form one coherent specification sufficiently closed for G5 to choose concrete production representations and migration shapes.
>
> Inspect the repository directly.
>
> Primary scope:
>
> - `openspec/changes/rework-model-strategy-trainer/**`
> - the overlapping `openspec/changes/expand-model-metadata-identity-and-structure/**`
> - research/design documents explicitly cited by those changes where needed to interpret an established requirement
> - current production/experimental code only when a design/spec statement relies on a current-code claim or migration assumption
>
> Do not let current implementation structure override the accepted design.
>
> Before auditing, reconstruct the source-authority hierarchy. Distinguish:
>
> - governing design decisions;
> - normative delta requirements/scenarios;
> - exploratory/research evidence;
> - current-code/migration evidence;
> - task completion claims;
> - intentionally deferred G5 implementation choices.
>
> Do not promote research terminology or experimental classes merely because they exist.
>
> Then perform separate audit passes.
>
> **Pass A — authority, identity and ownership**
>
> Trace logical run, participant, relationship, binding, route/view, activity, request/input/attempt, optimization unit, execution session, realization/composition, catalog/source identity, product/member/resource, runtime snapshot and metadata observation.
>
> For each determine:
>
> - who establishes it;
> - who owns current truth;
> - who may mutate it;
> - who may observe/project it;
> - what establishes identity;
> - what explicitly does not establish identity;
> - what survives restoration;
> - what creates a new incarnation.
>
> Find duplicated canonical state, conflicting writers, implicit Trainer/strategy/mode/metadata authority, or identity inferred from names, paths, roles, object identity or storage aliasing.
>
> **Pass B — revision, freshness and lifecycle**
>
> Inventory every distinct revision/version/generation/incarnation/session/attempt/current/final/prepared/published concept.
>
> Produce a non-substitutability matrix showing which meanings are distinct.
>
> Audit the specs for accidental substitutions, especially among:
>
> - authority/arrangement revisions;
> - participant/binding/relationship revisions;
> - mutable numerical state;
> - optimization-unit definition/state;
> - prepared executable generations;
> - execution sessions and attempts;
> - model-realization composition revisions;
> - catalog/model revisions;
> - product capture scope;
> - producer/source versions.
>
> Pay special attention to checkpoint-scoped finalization, stale preparation/publication, restoration and delayed observations.
>
> **Pass C — execution, effects and failure**
>
> Trace accepted work from readiness/admission through protected use, execution, derivative/contribution handling, retained Trainer mechanics, backend completion, outcome, cleanup/handback and observation.
>
> Inject failure before and after each meaningful boundary.
>
> Look for assumptions that Python return equals completion, exceptions prove no effect, one action has one success outcome, gradient availability authorizes an update, retries are safe, cleanup failure erases a known result, or missing observation proves no work occurred.
>
> **Pass D — independent progress and coordination**
>
> Treat input production, cache production, training actions, optimization units, validation, sampling, artifact publication, snapshot work and metadata delivery as independently progressing unless the accepted graph explicitly relates them.
>
> Find accidental global-step, end-of-step, sample-then-validation, queue-order, global-pause, or head-of-line-blocking assumptions.
>
> Identify every required wait/exclusion/version/completion relationship and whether unrelated work remains free to progress.
>
> **Pass E — persistence, restoration and observation**
>
> Cross-compare cached values, trained products, runtime snapshots, metadata snapshots/history and optional telemetry.
>
> Verify the specification consistently distinguishes:
>
> - produced / stored / published / admitted / consumed;
> - captured / current;
> - local / remote publication;
> - product completeness / runtime recoverability;
> - snapshot capture / durable publication / restore readiness;
> - origin outcome / metadata delivery;
> - required durable history / optional telemetry.
>
> Check partial, uncertain and external-effect cases.
>
> **Pass F — whole-run pressure cases**
>
> Trace at least:
>
> 1. ordinary SDXL-like training;
> 2. independently and jointly due optimization units;
> 3. routed losses with a frozen differentiable conduit;
> 4. bounded two-pass/SAM temporary mutation;
> 5. independent producer using accepted lagged state;
> 6. versioned cache production/consumption;
> 7. validation feeding accepted adaptive state;
> 8. staged topology replacement;
> 9. adapter product whose required base also changed;
> 10. partial multi-resource product publication;
> 11. same-run restoration with unfinished producer/optimization state;
> 12. restoration into a new execution session with late old-session results.
>
> For every case trace contract → accepted semantic state → preparation → execution → persistence/restoration → metadata/observation as applicable.
>
> A mention in one section is not sufficient. Verify the same identity, authority, revision, effect and outcome semantics remain compatible across all relevant specs.
>
> **Pass G — G5 readiness**
>
> Classify every remaining uncertainty as one of:
>
> - semantic contradiction — blocks G5;
> - missing semantic rule — blocks G5;
> - underspecified cross-spec correspondence — normally blocks G5;
> - wording/terminology ambiguity — correct before or during G5 depending risk;
> - deliberate implementation choice — belongs in G5;
> - later optional capability/optimization — does not block G5;
> - research-only question — does not block unless a normative requirement depends on it.
>
> Do not turn implementation choices such as Python/native execution, direct handlers, code generation, compiler substrate, storage format, final class names or ABI into blockers unless the normative semantics genuinely cannot be realized without deciding them.
>
> Also inspect both OpenSpec changes for duplicated `MODIFIED` requirements/scenario bodies and identify any drift. Treat the documented shared-boundary rules as synchronization requirements, not two independent authorities.
>
> Run the repository's applicable strict OpenSpec validation/checks after understanding how the project invokes them. Do not invent a validation command. Report validation failures separately from semantic findings.
>
> ### Finding discipline
>
> Do not immediately edit the specs.
>
> For every finding record:
>
> - ID;
> - severity: G5 blocker / high / medium / low;
> - audit pass;
> - exact files, requirement/scenario/section;
> - the two or more statements that conflict or the missing relation;
> - why it matters using a concrete execution case;
> - whether this is genuinely semantic or merely an implementation choice;
> - smallest plausible correction;
> - other specs that correction could affect.
>
> Do not report stylistic repetition merely because the OpenSpec is long. Repetition is a finding only when it can drift, contradict, or obscure authority.
>
> Do not “fix” a gap by inventing a new framework abstraction unless the existing accepted meanings cannot express the requirement. Prefer exposing the exact missing semantic relation.
>
> ### Required outputs
>
> Create a readable audit report containing:
>
> 1. reconstructed architecture/authority map;
> 2. identity and ownership matrix;
> 3. revision/version non-substitutability matrix;
> 4. cross-owner lifecycle/effect matrix;
> 5. pressure-case traces;
> 6. findings grouped by severity;
> 7. contradictions between the two overlapping OpenSpec changes;
> 8. explicitly verified areas where no issue was found;
> 9. unresolved questions that truly require a decision before G5;
> 10. deliberate implementation choices that should remain deferred to G5;
> 11. final verdict:
>    - G5 ready;
>    - G5 ready after listed bounded corrections;
>    - or G5 blocked by named semantic issues.
>
> For the verdict, explain exactly why. Do not use “the spec is large/complex” as evidence either way.
>
> The desired outcome is not more architecture. It is confidence that the architecture already selected is internally coherent enough that G5 can choose concrete representations without having to rediscover semantic ownership halfway through implementation.

That gives Work enough room to spend time on the job without just wandering around the repository.

Then I’d make the **fresh adversarial session much shorter and nastier**: give it the resulting audit report plus the repo and ask it to find false negatives, false positives, and places where the first auditor silently reconciled two incompatible requirements instead of reporting the contradiction.

That two-auditor setup should be substantially more useful than five increasingly self-confirming passes in the same conversation.
