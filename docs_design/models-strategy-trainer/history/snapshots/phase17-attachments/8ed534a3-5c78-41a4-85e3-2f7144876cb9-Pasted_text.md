## 1. cuTile: probably the obvious thing to try first

This one is almost unfairly well matched to your immediate situation.

PyTorch is already implementing essentially:

```text
Inductor IR
    ↓
TileKernelScheduling
    ↓
cuTile
    ↓
CUDA
```

with automatic ATen fallback for unsupported operations. [GitHub](https://github.com/pytorch/pytorch/issues/175311?utm_source=chatgpt.com)

And NVIDIA now supports:

```text
Python 3.14t       ✅
Ampere             ✅
RTX 3090 / sm_86   ✅
Ada                ✅
Hopper             ✅
Blackwell          ✅
```

cuTile Python explicitly added Python 3.14t support, and CUDA Tile IR added Ampere support in 13.2. NVIDIA's own table specifically lists the RTX 3090 under `sm_86`. [NVIDIA Docs](https://docs.nvidia.com/cuda/cutile-python/generated/release_notes.html?utm_source=chatgpt.com)

So your stack could become:

```text
torch.compile
     ↓
Dynamo
     ↓
AOTAutograd
     ↓
Inductor
     ↓
cuTile backend
     ↓
CUDA Tile IR
     ↓
3090 / 3080
```

No Triton.

No loss of autograd.

No loss of Dynamo.

No trainer rewrite.

No custom ML framework.

The downside is obvious:

**NVIDIA only.**

So I'd view this as the **practical immediate solution**, not necessarily the architecture you marry forever.

# 2. CubeCL: the one I'd most like to see exist

This is probably the most compelling **actual replacement architecture**.

CubeCL now targets:

- CUDA
- HIP
- Metal
- Vulkan
- WebGPU
- LLVM CPU

from the same compute abstraction. [GitHub](https://github.com/tracel-ai/cubecl?utm_source=chatgpt.com)

Meaning you could theoretically have:

```text
                   TorchInductor
                        │
                  CubeCL backend
                        │
       ┌────────┬───────┼───────┬─────────┐
       ↓        ↓       ↓       ↓         ↓
     CUDA      HIP    Metal   Vulkan     CPU
```

That's much nicer than:

```text
Inductor
   ↓
Triton
   ↓
CUDA / some AMD support
```

And we don't actually need to build a new compiler architecture.

PyTorch has already defined the extension point. Their Inductor-backend RFC says an out-of-tree backend can reuse Inductor's fusion/optimization and primarily provide:

- `Scheduling`
- `Kernel`
- `WrapperCodegen` [GitHub](https://github.com/pytorch/pytorch/issues/99419?utm_source=chatgpt.com)


Even better, the cuTile work is currently extracting shared **tile-oriented infrastructure** from Triton's implementation.

So rather than copying:

```text
TritonScheduling
```

today and maintaining a huge fork, the goal becomes something closer to:

```text
             TileKernelScheduling
              /              \
       cuTileScheduling    CubeCLScheduling
              |                 |
       cuTileKernel        CubeCLKernel
```

That's exactly where I'd want to attach.

### The annoying CubeCL issue

The biggest current problem isn't actually generating arithmetic.

It's integration with PyTorch-owned GPU memory.

CubeCL still has an open issue around directly accepting externally owned device buffers. That's precisely what we'd need for clean zero-copy `torch.Tensor → CubeCL kernel` interoperability. [GitHub](https://github.com/tracel-ai/cubecl/issues/291?utm_source=chatgpt.com)

You need:

```text
torch.Tensor
    │
    │ same allocation
    ▼
CubeCL kernel
```

not:

```text
torch
 ↓ copy
CubeCL
 ↓ compute
 ↓ copy
torch
```

That needs proper support for:

- external CUDA/HIP pointers
- lifetimes
- streams/events
- devices
- synchronization
- allocator ownership

None of those are conceptually difficult, but they're the sort of plumbing where bugs produce spectacular GPU memory corruption.

So **CubeCL is realistic**, but there's real integration work before you even start porting Inductor lowering.

# 3. TileLang is more realistic than I initially gave it credit for

I would absolutely evaluate this alongside CubeCL.

TileLang has moved pretty quickly. It's built over TVM and now supports targets including:

```text
CUDA
HIP
Metal
LLVM
WebGPU
CuTeDSL
```

and its current language layer is explicitly organized around shared multi-backend semantics. [GitHub](https://github.com/tile-ai/tilelang/blob/main/docs/get_started/targets.md?utm_source=chatgpt.com)

It also declares normal Python 3.14 support. [GitHub](https://github.com/tile-ai/tilelang/blob/main/pyproject.toml?utm_source=chatgpt.com)

And it's already designed to accept PyTorch tensors for JIT kernels.

So an Inductor backend could look like:

```text
Inductor IR
    ↓
TileLangScheduling
    ↓
TileLang kernel
    ↓
TVM
 ┌──┼────┬──────┐
CUDA HIP Metal LLVM
```

In some ways this could actually be **easier than CubeCL** because both Inductor and TileLang expose Python-facing compiler APIs.

The elephant in the room is your requirement:

### Python 3.14 != Python 3.14t

TileLang has native C++/TVM components:

```text
libtilelang.so
TVM FFI
```

and I haven't found an explicit guarantee that the whole stack is **free-threading safe**.

That's important.

It could install and run on 3.14t while silently causing CPython to enable the GIL, exactly like the Triton problem we're trying to escape.

So before choosing it I'd do a proper:

```text
TileLang
TVM FFI
native extensions
DLPack bridge
caches
JIT compiler state
```

free-threading audit.

If that comes out clean or easily fixable, **TileLang jumps way up the ranking.**

# 4. Fixing Triton remains annoyingly attractive

Even if we want to get away from Triton architecturally, I'd still investigate making it work.

Because there are thousands of things in the ecosystem like:

```python
@triton.jit
def some_obscure_kernel(...):
```

that you're going to encounter regardless of what Inductor does.

So ideally the eventual system isn't:

```text
Triton forbidden
```

but:

```text
generic compiled PyTorch
       ↓
CubeCL / cuTile / whatever

third-party Triton kernel
       ↓
free-threading-safe Triton
```

That gets you compatibility **without making Triton foundational**.

There's a big difference.

# What I wouldn't do

### Full Triton → CubeCL compatibility layer

Meaning:

```text
Triton Python
   ↓
TTIR
   ↓
translator
   ↓
CubeCL
```

Cool project.

Wrong solution here.

You'd inherit Triton's frontend semantics *and* maintain a compiler translation layer when Inductor already gives you a better neutral IR upstream.

I'd only consider this later if the goal became:

> run existing arbitrary Triton kernels on AMD/Metal/etc.

That's a separate project.

---

### Direct CUDA C++ Inductor backend

Technically viable:

```text
Inductor
   ↓
C++/CUDA codegen
   ↓
nvcc/NVRTC
```

But we'd basically find ourselves recreating a bunch of what Triton/cuda-tile/CubeCL exist to provide.

And now we're NVIDIA-specific anyway.

cuTile wins that comparison pretty decisively.

---

### CuTeDSL as the general backend

CuTeDSL is awesome for optimized NVIDIA kernels.

PyTorch already has a CuTeDSL template backend. [GitHub](https://github.com/pytorch/pytorch/blob/main/torch/_inductor/codegen/cutedsl/README.md?utm_source=chatgpt.com)

But it's much more naturally used for things like:

```text
GEMM
attention
convolution
specialized templates
```

than arbitrary:

```text
some bizarre fused pointwise +
broadcast +
reduction +
gather +
random +
cast
```

Inductor kernels.

And critically for us, the current CUTLASS release says **3.14t is supported with the GIL enabled**. [GitHub](https://github.com/NVIDIA/cutlass/discussions/3321?utm_source=chatgpt.com)

So it doesn't solve the original problem anyway.

---

### Helion

I like Helion quite a lot, but as a complementary system.

Current Helion can target Triton and has experimental CuTe/TileIR paths. [GitHub](https://github.com/pytorch/helion?utm_source=chatgpt.com)

I'd happily use it for:

```text
"we need a custom optimized attention kernel"
```

I wouldn't make it responsible for compiling every arbitrary Inductor fusion group.

---

### IREE / StableHLO / whole-graph compiler

Something like:

```text
torch.export
    ↓
MLIR
    ↓
IREE
```

could theoretically eliminate Triton entirely.

But then we're changing compilation models dramatically.

Training, mutations, dynamic behavior, custom autograd, graph breaks and arbitrary third-party PyTorch code become the hard problems.

That's exactly the “end up with crippled capabilities” trap you're trying to avoid.
