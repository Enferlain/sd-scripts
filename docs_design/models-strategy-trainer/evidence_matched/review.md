## Actionable issues (none blocking)

1. **`equivalent()` silently inherits the comparator's property/operand semantics** (lifetime_ir.py:283-299). Its own checks (names, result counts, types) are not sufficient alone; safety relies on xdsl 0.74's `is_structurally_equivalent` also comparing properties, operands against the mapping, and block arguments. That behavior is currently pinned only *indirectly* through `verify_saved` tests (`test_cold_recipe_correspondence`, `test_framework_equivalence_detects_forward_and_ordered_use_changes`). Recommendation: add a colocated unit test of `equivalent` itself that mutates only a `RecipeOp.values` property (and only an operand edge) and asserts `False`, plus a comment naming the comparator guarantees as load-bearing. Otherwise an xdsl upgrade that weakens property comparison would silently weaken cold verification.

2. **`verify_saved` has no artifact key whitelist** (lifetime.py:482-510). Unknown fields (`nodes`, arbitrary `profile`, future fields) are accepted and ignored. Deliberate for observations, but an explicit allow-list (`accepted`, `prepared`, `manifest`, `schema`, `framework`, `target`, `profile`, `accepted_sha256`) with "unknown field" rejection would prevent a later caller mistaking an unverified field as checked — mirroring what B's `check_plan` already does for plan properties ("unknown executable property").

3. **`capture_cases` hard-codes default scope names** (`"training"`, `"consumers"` at capture.py:72-73). It is only valid for default-named artifacts; renamed coverage currently goes through `pressure`/`check(prefix=...)` in tests. Either take the names from the artifact/profile or document the constraint in the docstring, so a future renamed capture doesn't fail confusingly.

4. **Accept-level redundancy is only rejected at the target boundary.** `verify()` allows e.g. two `ProducerOp`s/`GroupOp`s under run or duplicate terminators in a body (settlement coverage is still exact); `target_profile`'s `one(...)` rejects them only in `prepare`. Not a bypass (prepare/verify_saved always run before execution), but if `accept()` is ever used standalone as a semantic gate, duplicate-producer documents would pass acceptance. Consider an explicit "at most one producer/group per run" check in `verify` if that boundary matters.

5. **B fresh-process cold run of the *new* saved-text path is not itself in a child process.** The lifetime case has the required fresh/-O cold child; for the matched B controls, `saved_text`/`saved_manifest` validation is exercised in-process (`test_same_b_parameters...`, `test_xdsl_cold_claims...`) and in `capture_controls` (same process), while the pre-existing fresh/-O B children predate the saved-text parameter. The plan's per-case receipt (requirement 3) asks for fresh-process cold-load "for every matched case"; closing this in `.31.25.7` (one child run through the saved-text path with authors/Pliron blocked) would make the B receipt airtight.

6. **Minor parsing laxity in policy numbers** (lifetime.py:53-68): `int(" 3 ")`, `int("1_0")`, `float("1_0.5")` are accepted for `horizon`/`ready`/`workers`/`learning_rate`/`after_window`. Harmless (values are re-checked against exact pins or by the oracle), but normalizing with a stricter regex would keep diagnostics clean.

7. **Nits:** the port-role zip in `plan()` (lifetime.py:416-420) relies on the pinned `members == 2`; if the target bound is ever relaxed it fails via `zip(strict=True)` rather than a diagnostic — fine, but a comment would help. `lifetime_demo --load` executes the shared pressure harness rather than performing cold-only verification; that's documented, just be aware the demo is not the cold witness.

## Assessment

The slice does what it claims and no more: reciprocal B/opaque controls with correct ordering of the valid-unfused-execution-before-forged-rejection correction; an independently verified typed xDSL lifetime representation whose cold correspondence is regeneration-based, manifest-equal, and observation-blind; deliberate, correctly scoped reuse of the existing owner engine/bindings/witnesses/oracle; and honest, verifiable bounded claims (counts, hashes, and open items all check out, including the still-open `.31.23` progress failure and `.31.25.3+` work). Coverage is meaningful rather than voluminous — the corruption matrices target real semantic boundaries (pending-keeps-alive, all-and-only settlement, stream/model association, gradient chain, protected read state, manifest/manifest-field drift, factory ordering). I'd ask for items 1, 2, and 5 to be addressed (small, and they harden exactly the cold-verification boundary this milestone leans on) before marking `.31.25.7`; items 3-4-6-7 are optional polish.
