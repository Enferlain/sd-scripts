## 3. Finding

### P1-REV-01 — Medium: shared structural targeting has no explicit applicability rule for a participant without family components

**Classification:** semantic omission / wording ambiguity with a concrete interpretation risk; cross-artifact scope mismatch. This is not a request for a new representation or universal structural catalog.

**Exact source relationship:**

1. `openspec/changes/rework-model-strategy-trainer/specs/loaded-model-components/spec.md`, **“Top-level components remain the highest generic control surface”**, lines 38–56, requires independently managed participant state outside one source model *without forcing that state into family component declarations*. Its **“Additional run participant is not one loaded-model component”** scenario names adapters, teachers, reward models, and other participants. [LoadedComponents]
2. `openspec/changes/rework-model-strategy-trainer/specs/training-optimization/spec.md`, **“Strategy declares semantic training subjects”**, **“Semantic membership is authority-qualified”**, and **“Trainer owns standard realization and mechanics”**, permits participant/substructure subjects and learned capability state, with live resolution owned by optimization. These meanings are not limited to model-family components. Design D9 and the side-network case carry the same separation. [Optimization] [NonSDCases]
3. `openspec/changes/rework-model-strategy-trainer/specs/optimization-target-refs/spec.md`, **“Shared optimization target refs”**, lines 3–25, gives unqualified module/parameter scenarios that require a **declared model component**. **“Module and parameter refs expand from declared components”**, lines 69–77, requires expansion from an accepted participant's declared top-level components. Unlike the component-target requirement at lines 55–67, this rule does not qualify itself as applying only to **model-owned structure**. [Targets]
4. The companion `openspec/changes/expand-model-metadata-identity-and-structure/specs/optimization-target-refs/spec.md`, **“Target refs can reference accepted structural identities”**, lines 3–30, allows absent catalog/structural associations while requiring accepted participant identity. That solves missing catalog evidence, not missing family-component ancestry. The companion structural design explicitly derives its model paths from family components. [CompanionTargets] [CompanionStructure]

**Concrete consequence:** declare an independently managed learned loss-weight vector or small auxiliary participant `A` alongside an SDXL backbone, with accepted training subject `A.weight`. `A` has its own incarnation, bound state, and optimization responsibility but is not a component declared by the SDXL family. Optimization must resolve its trainable parameter under the accepted subject meaning. A consumer using the shared parameter-ref contract must also supply a declared family component and component-local selector, which this filing does not have.

There are materially different possible implementations: fabricate a family component; attribute the parameter to a host component despite independent ownership; bypass shared refs through another participant-substructure representation; or provide a participant-root target. The sources do not establish which applicability relationship is intended. Fabricating component ancestry contradicts the loading boundary; borrowing host identity can confuse ownership, alias handling, or grouping; a distinct target path needs an explicit relationship to the supposedly shared target model. Returning a raw parameter pointer would not satisfy authority-qualified semantic membership. This is an implementation decision that cannot be derived from the current universal component wording alone.

The finding is deliberately narrower than “standalone participants cannot be trained.” They can have specialized trainable results, and many independent teachers/reward models may themselves have genuine family declarations. The problem is that the requirements do not clearly bound shared refs to those component-backed cases or establish their applicability to the admitted component-free case. Catalog omission is not a substitute for that decision. Likewise, adapter **host-target provenance** is not automatically the semantic owner identity of adapter state; those associations need to remain distinct even when both are retained.

**Smallest plausible correction:** explicitly limit family-component derivation and existing component-qualified selector compatibility to targets with genuine model-component provenance. Establish that admitted participant-owned substructure without that provenance can still be addressed under its authority-qualified participant meaning, and state how Trainer optimization's trainable references relate to shared target refs in that case. Add one positive scenario resolving a learned participant's parameter without creating family inventory, and one rejection scenario for invented component ancestry or stale participant context. No class name, string syntax, catalog identity, or universal root-field layout is needed to settle this meaning.

**Neighboring requirements affected:** shared module/parameter target scenarios and expansion; loading's extra-participant boundary; authority-qualified optimization membership; companion optional structural associations. Adapter/method trainable provenance and component learning-rate compatibility must retain genuine host associations without turning them into a false component declaration for every independent learned owner. Keep existing selectors/grouping behavior for actual component-backed targets. [Targets] [LoadedComponents] [Optimization] [CompanionTargets] [AdapterTargeting]

**Disposition:** Pass 1 owns the applicability clarification; Pass 6 should verify structural associations and retained selector compatibility, and Pass 3 should verify resulting member/group resolution. Concrete reference storage and API shape remain G5 choices. The semantic scope question is not resolved merely by postponing a type layout.

## 5. Verified areas and concrete case reasoning

These are source-level checks of architectural meaning. They do not certify an integrated implementation.

### Contract, fulfillment, and readiness

The pre-existing contract supplies the supported meaning before authoring; explicit Python composition selects and wires the filing. Fulfillment checks the complete definition, derives one obligation set, and produces accepted arrangement/authority only on success. Later producers supply evidence, and the same system checks it at the earliest authoritative point. Normal Trainer construction cannot accept an unchecked strategy/mode/objective set. Capability requests can parameterize a provided capability within accepted bounds without selecting a different implementation. [D1] [D2] [D3] [Contract]

**Ordinary maintained case:** select SDXL representation, conditioning, objective, subjects, optimization policy, and requested capabilities. A missing VAE pairing or known unsupported product fails fulfillment; backend-specific realization evidence remains an explicit obligation. The selected SDXL loader supplies candidate components/evidence; the authority publishes bindings; preparation coordinates routes and optimization. Training receives admitted input and current views and executes selected domain computation. Trainer retains standard backward, clipping, advancement, progress, and triggers. It does not infer SDXL anatomy or ask the authoring interface to repeat its choices. [OrdinaryCase] [Preparation] [StandardMechanics]

The current launcher independently constructs strategy and mode, and the current loop calls `process_batch` with Trainer projections. Inspection confirms this migration contrast. It does not establish the target API or justify retaining that runtime dialogue. [CurrentLauncher] [CurrentLoop]

### Dynamic and stateful selected behavior

Acceptance retains policies, state definitions, initialization rules, observation dependencies, and continuation contributions, rather than one fixed outcome. Adaptive behavior can consume prior losses and change later computation within accepted bounds. The state owner advances it; Trainer routes required observations. Logging a copy is optional under its delivery policy, while required algorithmic feedback is a runtime exchange whose retry cannot be confused with log retry. [DynamicExecution] [Synthesis] [Observation]

**Adaptive case:** an objective sampling policy updates from an accepted observation. It does not gain optimizer authority or require re-fulfillment for each update. Replacing its observation producer with different meaning, or changing a participant dependency, instead requires the declared preserve/migrate/reinitialize/retire treatment before dependent work resumes. Failure after a possible state update does not establish unchanged state just because no result returned. Exact continuation requires the owner's contribution. Those rules are present in complete requirement/scenario text, not inferred from a closure executing successfully. [DynamicExecution]

### Participant identity, uses, and frozen gradient paths

Different declarations sharing a checkpoint get distinct incarnations. Conversely, teacher/student **uses** of one participant do not create duplicate participants. Each invocation has its own view, order, and gradient need. A no-gradient teacher use can coexist with an adapted differentiable use of the same base only when preparation and current-use protection support them. Shared mutable adapter toggles require serialization and restoration; uncertain restoration gates dependents without pretending the action succeeded. [ParticipantState] [ParticipantUses]

**Frozen gradient-path case:** a frozen base propagates derivatives to a trainable control branch. The base remains outside optimization membership but inside execution/preparation and numerical-lifetime requirements. Unsupported routing fails readiness; “frozen” does not authorize detachment. Thus execution membership, gradient participation, trainability, and product membership have separate owners. P1-REV-01 concerns how an independently managed branch's targets are represented when it lacks family-component ancestry, not whether this gradient distinction exists. [DifferentiatedExecution] [NonSDCases]

### PEFT, independent participants, and direct-plus-PEFT composition

The target separates authored host intent, governed target resolution, method-specific realization, relationship publication, and later optimization grouping. PEFT method availability does not silently expand a strategy's declared support. Attachment does not implicitly create the adapter participant; target-local modules/shared banks need not each become participants. State-only adapters need no fake forward route. [D12] [Adapter] [AdapterTargeting] [ParticipantState]

**Joint training case:** an accepted unit or coordinated units select base and adapter semantic subjects. Governed PEFT resolution supplies host targets; the method supplies adapter state/trainables; optimization owns the resulting membership and mechanics. Product support follows explicit declarations. An adapter-only output cannot claim to contain updated base weights; a compatible base dependency or expanded product coverage is required. No exclusive adapter/fine-tune runtime classification follows. Genuine host-target provenance remains valuable, but does not settle the component-free target case. [PEFTCase] [Optimization] [Products]

Retained main-spec obligations were checked: broad adapter applicability, typed helpers, genuine grouping boundaries, method-local settings, LoRA math/provenance, VeRA shared projections and reconstruction, parameter-native trainables, and public component selectors/order/labels remain. The deltas explicitly displace permanent `AdapterMode` orchestration and optimization-owned PEFT host selection. Mode-named scenario headings preserved for matching have replacement bodies. The rework does not rely only on prose to override those old actors. [Reconciliation] [MainAdapter] [MainTargeting] [MainLoRA] [MainVeRA] [Targets]

### Independent production and whole-run ownership

Accepted execution covers long-lived input activities, requested capabilities, repeated actions, transitions, handoffs, and independent clocks. Cache production owns its traversal/storage continuation; a live provider owns selection/packing/exposure continuation; each consuming coordinator checks admission under its own existing obligations. A published cache value can be admissible for inference but inadequate for a training derivative path. No universal training-input gateway or completed-dataset barrier is imposed. [WholeRun] [Input] [CapabilityExecution]

**Independent producer case:** encoding completes out of order while ordinary training or capability work progresses. Production completion preserves actual work/source provenance; admission checks its association and accepted freshness/lag rule. Readiness does not establish consumption or an optimizer contribution. The producer's continuation and the optimization owner's progress remain separate but correlatable. Mixed-source provenance permits evaluation of admissibility, not automatic approval of mixed-state work. [Input] [Correlation]

The bounded experiment does demonstrate an explicit provider lifetime beside action wiring and owner-correlated attempt outcomes. Its one-feed/linear-action restrictions, manually driven producer completion, missing capability/stage/snapshot machinery, and trusted callbacks are expressly documented. Those limitations are not requirements of the accepted whole-run mechanism. A `Callable` selected as accepted runtime behavior is not inherently the forbidden broad strategy-authoring callback. [ExperimentDescription] [ExperimentImplementation]

### Coordinated stage changes

**Stage case:** progressive distillation updates teacher state, optimizer realization, EMA behavior, and stage-local progress. Participant continuity is judged under accepted meaning; an optimizer object alone does not establish a new unit; affected operation/backend/window state needs its accepted continuity treatment. The authority and relevant owners publish coherent current state before dependent work resumes. Replacement-only candidates can be built privately, while destructive mutation withdraws affected guarantees before mutation. This is compatible with several declared writers and incompatible with unilateral local installation of an interdependent stage. [NonSDCases] [Invalidation] [Preparation] [Transitions]

Ordinary selected packing/schedule changes within accepted bounds do not automatically become the same kind of stage amendment. Changes outside those bounds follow an applicable governed transition, or new fulfillment if they require another contract/profile. The distinction is semantic and source-backed; the concrete proposal/coordinator types remain deferred. [D10] [Invalidation]

### Substantial research authority alongside retained Trainer duties

**Two-pass case:** the offered narrow profile grants the accepted region two backward passes, scoped parameter perturbation/restoration, and intermediate gradient handling. Trainer/run coordination retains due selection, entry/readiness, initial clearing, handback checks, final clipping/optimizer/scheduler advancement, final clearing, progress, triggers, and failure coordination. Ordinary actions in the same run keep standard ownership. A wrapper secretly advancing an optimizer does not gain permission from library availability. [Grant] [GrantedExecution] [Contract]

The executor receives admitted values, current scoped routes/parameters/gradient access, required selected computation, and accepted owned-state/RNG inputs. It receives no whole Trainer or final advancement handle under this split. Branching on gradients or updating accepted statistics can remain ordinary selected Python without numerical capture or an authoring callback. Declarations do not prove hidden mutation impossible. Backend safety and usable second-pass gradients are readiness/handback obligations; an unsupported backend must be rejected before execution. [Grant] [Preparation] [TwoPassProposal]

Temporary parameters and intermediate gradients are protected from conflicting actions, capability readers, preparation publication, and snapshots throughout actual use and handback into retained mechanics. Failed second-pass work does not authorize stepping even after clean parameter restoration. Failed restoration or uncertain handback withholds affected live usability until accepted recovery; unrelated work can proceed only where the accepted failure policy and real resource dependencies permit it. Exact snapshots for this profile require coherent quiescent, unperturbed boundaries. None of this makes the region another Trainer or grants unrestricted strategy takeover. [GrantedExecution] [ProtectedUse] [Restoration]

The inspected two-pass test supports local phase non-overlap, pre-edit rejection, restoration plus final-gradient handback, and blocked advancement after selected failures. Its handback uses booleans and a directly inspected single parameter. It does not implement capability-reader exclusion, snapshot coordination, or backend-certified restoration. The governing design explicitly acknowledges those limits; no broader enforcement guarantee is accepted from the test. [TwoPassTest] [Grant] [ExperimentDescription]

### Metadata, observation, products, and recovery owners

Loading facts describe candidates; authority publication establishes current bindings. Durable composition derives from accepted publication and named readiness-checkpoint finalization. Metadata stores supplied incarnation/revision/state-provenance correspondence rather than deciding current readiness. Resource physical sharing remains observation-local evidence; it cannot merge participants or optimization units. Component public labels/order remain presentation facts. [LoadedComponents] [Metadata] [MetadataBoundary] [Observation] [CompanionTargets]

**Persistence/recovery check:** a stable product capture may publish after later live topology changes while retaining its captured meaning. Export transformations do not silently mutate the run. A written product can remain known successful even if cleanup makes live training unsafe, or if independent runtime-snapshot publication fails. Exact continuation requires the authority and all necessary owner contributions, fresh readiness, and a new execution session; it does not recover identity from a checkpoint path or recreate defaults after a contributor fails. These are consistent ownership boundaries; detailed formats, delivery policy, and recovery execution belong to later passes. [Products] [Restoration]

## 6. Deferred choices, coverage limits, and later-pass questions

No finding is issued for absent Python class names, identity encoding, module layout, lock choice, concrete installation mechanism, decorator design, native coordinator, numerical capture, or an extra executable IR. Those are implementation/representation choices whose accepted semantics must be preserved. A direct handler can suffice for a closed operation; an accepted description remains necessary wherever another owner relies on dependencies, lifetime, effects, or authority. The sources do not require every private numerical operation to be visible. [D10] [Synthesis] [DeferredShapes]
